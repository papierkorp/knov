## breaking changes

- api: `POST /api/files/export/zip` and `POST /api/files/export/markdown-converted` were removed. use `GET /api/exports/files` / `GET /api/exports/markdown` instead (the archive is streamed directly, no more building it in memory first)
- logging: the `dokuwiki-export` log key was removed, the bulk export logs (files, markdown, pdf) now go to the `export` log. an existing `dokuwiki-export.log` can be deleted
- api: `POST /api/files/rename/{filepath}` no longer always answers with an `HX-Redirect` to the renamed file - it only redirects when the `HX-Current-URL` request header points at the renamed file (`POST /api/files/move-folder/{folderpath}` does the same for a file inside the moved folder), otherwise it answers with an `HX-Trigger` notify toast. scripts that relied on the redirect should read the new path from the response body instead
- themes: the dropdown menu classes `fp-menu-wrap`, `fp-menu-btn`, `fp-menu`, `fp-menu-item` and `fp-menu-item--danger` were renamed to `menu-wrap`, `menu-btn`, `menu`, `menu-item` and `menu-item--danger`. update custom css and custom themes that target the old names
- links: link paths are now percent-decoded exactly once everywhere (rendering, link metadata, rename and media relocation), and a renamed or relocated link is written percent-encoded (`[x](new%20name.md)`, `[[a%25b]]` for a file `a%b.md`) so it reads back unchanged. a hand-written link with a literal `%XX` in a filename (`[x](a%41.md)` for a file named `a%41.md`) now means the decoded name (`aA.md`) for link metadata and renames too, like it already did when rendering - write the `%` as `%25`
- markdown links: `.md` is only added to a link path without any extension (like wikilinks already do), so `[x](sub.index)` now opens `sub.index` and `[x](notes.txt)` opens `notes.txt`. a link to an extensionless note whose name contains a dot (`[x](v1.2 notes)`) has to be written with the extension (`[x](v1.2 notes.md)`)
- api: the `parents` of `POST /api/metadata/parents` (and other parent values) are no longer percent-decoded - send the plain file path (`docs/a b.md`), not an encoded url (`/files/docs/a%20b.md`). a `#`, `?` or `|` in a parent is now part of the filename instead of cutting it off
- markdown links: a link with any scheme (`mailto:`, `tel:`, `ns:page`) or a `//host` is now external and no longer routed to `/files/`, like it already was for link metadata - before only `://` links were. only `http:`, `https:` and `mailto:` links stay clickable, a link with any other scheme (`tel:`, `ns:page`, `obsidian://...`) is shown as plain text. a markdown link to a file whose name contains a ":" before the first "/" has to encode it (`[x](ns%3Apage.md)`) or use a wikilink (`[[ns:page]]`)
- index/book editor: a file entry is now typed and posted as the plain file path (`entries[][value]` of the index/book save api, `a b.md`) and stored url-encoded in the `[[...]]` link. saving the editor rewrites every file entry in that encoded form - a value sent already encoded (`a%20b.md`) is encoded again and points at a file literally named `a%20b.md`. send the plain path instead
- index/book editor: the section of a file entry has its own field (`entries[][section]`, the heading text or id) - a `#` or `|` in `entries[][value]` is now part of the file name, so `a.md#My Section` has to be sent as `a.md` plus section `My Section`. saving through the editor stores a section as its heading id (`#my-section`) and drops a hand-written `|alias` on an entry
- links: links inside inline code or fenced code blocks are no longer rendered as links (they already weren't counted as links). a markdown link to a `/files/` url without extension (`[x](/files/docs/a)`) now points at `a.md` like link metadata reads it - link a folder with a trailing `/`. a markdown link destination starting with an unclosed `<` (`[x](<a.md)`) is no link anymore, like in the rendered page. media relocation reads a markdown link without leading `/` (`![x](sub/a.png)`) like it renders (see the bare links note below). the dokuwiki import links `[[v1.2 notes]]` to the note `v1.2 notes.md` - only a known media extension makes a `[[...]]` link a media link
- links: an html entity in a markdown link or html src/href path (`[x](a&amp;b.md)`) now means the character it stands for (`a&b.md`) for link metadata and renames too, like it already did when rendering - a file with a literal `&` followed by an entity name in its name has to be linked with the `&` written as `%26`. a percent-encoded space at the start or end of a link path (`[x](%20a.md)`, `[[a.md%20]]`) is now part of the file name instead of being trimmed. an unclosed `[[wikilink` or one spanning a line break is no longer counted as a link or rendered
- links: quotes in a markdown link rewritten by rename or media relocation stay unencoded
- api: `POST /api/media/upload` reads `context_path` as the url path of the page the file is uploaded from (`/files/edit/<path>` or `/files/<path>`, percent-encoded like the browser's `location.pathname`) instead of the bare file path, and a page that isn't a saved file (`/files/new/...`) is answered with `400`. the media file now lands in the doc's real folder (`media/x (1)/pic.png`, before `media/x%20%281%29/pic.png`). a link the old upload inserted for such a folder now reads as the missing `media/x (1)/pic.png` - fix them with "Repair Broken Links" on the admin page, which suggests the media file the link points at. the response has a new `link` field, the ready-to-insert markdown link
- api: `GET /api/files/autocomplete`, `GET /api/media/autocomplete` and `GET /api/files/headers` take an optional `link=wiki|markdown` and then also return each suggestion as ready-to-insert link text (`link` in json, `data-link` on the html list item) - insert that instead of building the link from the plain path (`value` / `data-value`), which isn't encoded for a link
- files: new file and folder names can't contain `#`, `?`, `|`, `[`, `]` or `\` or start or end with a space anymore - creating, renaming or moving a file or folder, renaming media and saving a filter or tracker with such a name is answered with `400`. existing files with these characters (git sync, copied in by hand) keep working and can still be moved to another folder or renamed to a valid name - rename them if you want to link them without encoding
- links: a markdown or wiki link starting with `./` or `../` (and a bare `.` / `..`) is now read relative to the folder of the doc it is written in - in `sub/n.md`, `[x](./a.md)` opens `sub/a.md` (before it opened `a.md` in the docs root) and `[x](../a.md)` opens `a.md`. a `../` climbing above the docs root stops there. wikilinks without `./` or `../` (`[[a]]`) are still read from the docs root, bare markdown links see below. if you wrote `./` links meaning the docs root, write them with a leading `/`
- links: moving or renaming a file now also rewrites the `./` and `../` links inside the moved file itself, so they keep pointing at the same targets from the new folder (only links whose target exists, links between files moved together in a folder move stay as written). links in other files pointing at a moved file keep their relative form too
- links: a link without `media/` prefix to a file in the media folder (`[x](doc.pdf)`, `[[pic.png]]`, `[id]: doc.pdf`) now opens that media file, like link metadata already read it (before it opened the missing `/files/doc.pdf`), and renaming the media file rewrites these links too. a reference definition to a media file that isn't an image opens its media page. a `[[https://...]]` wikilink links its url instead of a missing file. html `src` / `href` paths are read like markdown links everywhere. outbound links and the broken links scan show every target with its `docs/` or `media/` prefix, and a link of a doc to itself is no longer listed as outbound or inbound link. nothing to do
- links: a bare markdown or html link - no `./`, `../`, leading `/` or `media/` (`[x](a.md)`, `![x](pic.png)`, `[id]: a.md`, `<img src="pic.png">`) - is now read from the folder of the doc it is written in, like `./a.md` (CommonMark / GitHub behaviour): in `sub/n.md`, `[x](a.md)` opens `sub/a.md`, before it opened `a.md` in the docs root. `[x](/a.md)`, `[x](/files/a.md)`, wikilinks (`[[a]]`) and `media/...` links (what upload and the editor insert) are read as before. links in docs at the docs root don't change. to keep the old targets, run "Scan Bare Links" in "Bare Links Migration" on the admin page: it lists every bare link whose target changed and rewrites the selected ones to their docs-root form (`/a.md`, `/media/pic.png`, a `/files/` url in html). renaming or moving a file keeps a bare link bare (written from its doc's folder), moving a doc now rewrites its own bare links too, and filter indexes link their files with `/a.md`. the help page lists the link rules
- links: a `../` link climbing above the docs root (`[x](../../a.md)` in `sub/n.md`) still opens the file it stops at (`a.md`), and "Repair Broken Links" now lists it as "climbs above the docs root" with that file as suggestion - the repair writes the link without the extra `../`
- tables: links in the cells of the interactive table view (`[[note]]`, `[x](a b.md)`, `./` links, anchors) now open the file like in the rendered page, before a wikilink stayed plain text
- api: the `select` mode of `GET /api/media/list` was removed (its list called an editor function that doesn't exist), use the default or `compact` mode
- themes: the template function `urlPathSegment` was removed, use `{{fileHistoryURL .Data.FilePath}}` for a file's history url
- api: file lists (`GET /api/files/list`, search, browse, filter results as json) give a docs file's `path` with its `docs/` prefix (`docs/notes/a.md`), like metadata paths - before it was `notes/a.md`. a docs file in a top-level folder named `docs`, `media` or `files` (copied in or synced with git) no longer shares its metadata with the media or docs file its path read as without the prefix
- urls: the `/files/`, `/files/edit/`, `/files/edittable/` and `/files/history/` pages and the `/api/files/content/`, `rename/`, `move-folder/`, `delete/`, `delete-folder/`, `versions/` (`diff/`, `restore/`) and `/api/metadata/rebuild/` routes read the path after the route prefix literally as a docs-relative path - `/files/docs/a.md` is now the docs file `docs/a.md` (`data/docs/docs/a.md`), not `a.md`, and `/files/media/x.md` is the docs file `media/x.md`, not the media file. bookmarks and scripts using `/files/docs/<path>` for `<path>` have to drop the `docs/`. the `context_path` of `POST /api/media/upload` is unaffected
- api: a `filepath` (and `file` of `/api/chat/messages`, `conflict` of `/api/links/conflicts/diff`) query / form param that names an existing file is its metadata path - `docs/notes/a.md` or `media/pic.png`, like `path` in file lists - and an unprefixed value is answered with `400`. this affects `/api/metadata*`, `/api/links*`, `/api/components/table`, `GET /api/editor`, `GET /api/editor/tableeditor`, `/api/files/{raw,header,views,overview,form,metadata-form,metadata/form,export/markdown,export/pdf,todo-toggle,todo-cleardate,convert-to-markdown}` and `/api/chat/messages` - scripts have to prepend `docs/` (or `media/`). the new path of `POST /api/metadata/path` (`newpath`) is a metadata path in the same folder as `filepath` too. paths a user types stay docs-relative and are read literally: the `filepath` of the save apis (`/api/files/save`, the editors, `/api/files/section/save`), the `name` / `target` of rename and move, `prefillpath` - `media/x.md` there is the docs file `docs/media/x.md`. the kanban apis (`/api/kanban/card/move`, `/api/kanban/{board}/events`) still take the docs-relative path
- links: a `/files/<path>` link (markdown or html) is now the docs-relative path taken literally - `/files/docs/a.md` is the docs file `docs/docs/a.md` (before `docs/a.md`) and `/files/media/x.md` is the docs file `docs/media/x.md` (before the media file), so a docs file in a folder named `docs`, `media` or `files` can be linked. a link written `/files/docs/<path>` (the dokuwiki import and old versions wrote them) has to drop the `docs/`: `/files/<path>` - "Repair Broken Links" on the admin page lists them. links written `media/...`, `./media/...`, `../media/...` or `/media/...` still open the media folder, `[[docs/media/x]]` names a docs file with its `docs/` prefix, and a bare, `./` or `../` link from a doc inside a folder called `docs`, `media` or `files` stays in that folder (before it read as the media folder / docs root). renaming or moving such a file writes `/files/media/x.md` where a relative link would read as media, the editor inserts `[[docs/media/x]]` for it
- api: the `parents` of `POST /api/metadata/parents` have to be metadata paths (`docs/a.md`, `media/pic.png`) - a parent without `docs/` or `media/` is answered with `400`. the filter criteria `child-of`, `parent-of` and `ancestor-of` compare metadata paths, so a saved value naming a docs file in a folder called `docs`, `media` or `files` needs its `docs/` prefix. a filter index links a docs file in a folder called `media` with its `/files/` url, a filter used in a book lists it as `docs/media/x.md`
- files: the metadata (tags, parents, editor, created date, references) of a docs file in a top-level folder called `docs`, `media` or `files` was stored under the path without that folder (`docs/media/x.md` as the media file `media/x.md`, `docs/docs/x.md` and `docs/files/x.md` as `docs/x.md`). the "Reserved Folders Migration" on the admin page moves such a record to the file's own `docs/...` key unless a file still lives at the old key (the record then belongs to that media or docs file and the docs file starts without metadata - set its tags again; `docs/docs/x.md` and `docs/files/x.md` shared one record, only one of them keeps it). a saved filter or tracker whose id starts with `docs/`, `media/` or `files/` and whose paired file lives at the docs root without that folder is renamed to the id without it by the same migration. the app no longer runs it on start - run "Migrate Reserved Folders" once after upgrading if you have files in such folders, it can be run again safely
- files: new files, folders, filters, trackers, kanban boards and auto-create-tag folders in a top-level folder called `docs`, `media` or `files` are allowed again (`docs/media/x.md` is the docs file `data/docs/media/x.md`) - before they were answered with `400`. the setting values stay docs-relative
- links: ascii control characters and "`" in a file name are now percent-encoded when the app writes a link to it (rename, move, editor autocomplete), so the link reads back as that file in link metadata and the rendered page. nothing to do
- links: the link scanner now reads markdown like the rendered page in more places: a link in an indented code block or an html comment (`<!-- [x](a.md) -->`) is no link anymore, an escaped `\[x](a.md)` is no link, and a destination or title on the next line (`[x](\na.md)`, `[id]:\n  a.md`) and backticks inside a destination (`[x](a`b`.md)`) are links like on the page. nothing to do
- links: markdown images are rendered from the same target link metadata reads - a bare `![x](pic.png)` that exists only in the docs folder is a `/files/` image (before a 404 `/media/` preview), an image whose name ends with a space renders, and images in the cells of the interactive table view render with their `/media/` url like on the page (before the src was relative to the page). nothing to do
- editor: the live table of contents of the codemirror editor is listed by the server (`POST /api/editor/toc`, form `content`, answers the headings with level, text and line) instead of by a copy of the heading rules in the editor script, so it shows the same text as the table of contents of the rendered page. a dokuwiki `<catlist>` is converted to an html anchor (also in markdown output), a link to the browse page. a header / footer zone of the pdf export that is one markdown image is read with the link scanner. nothing to do
- links: a "|" in a link path that rename, move or media relocation writes into a table row is escaped (`\|` in a markdown link, `%7C` in an html href), so it no longer ends the cell. nothing to do
- api: `POST /api/kanban/card/move` (`filepath`), `POST /api/kanban/{board}/order` (the paths in `order`) and `GET /api/kanban/{board}/events` (`file`) take the card's metadata path (`docs/projects/a.md`) like the other file apis - a path without `docs/` is answered with `400`, the move answers the new path with its `docs/` prefix. a custom theme's board script has to send the `data-filepath` of the cards as rendered. nothing is stored differently
- files: a book entry `[[...]]` is read like a wikilink to it everywhere (`[[docs/media/x]]` is the docs file `docs/media/x.md`, a `media/...` entry is a media file and is not included), the file tree's delete / rename / link buttons address a docs file in a folder called `docs`, `media` or `files` by its own path, an upload from a doc in `docs/media/` is stored in `media/media/...` (mirroring the doc's folder) and the link display text mode "filepath" shows the docs-relative path of a docs file again. nothing to do
- themes: the builtin theme builds the file, editor, history and kanban urls with the `urlPath` / `urlQuery` template functions, so a file or folder name with `%`, `&`, `+`, `#` or a space works in them. a custom theme that writes `/files/{{ .Data.FilePath }}` or `?filepath={{ ... }}` by hand has to use `{{ urlPath .Data.FilePath }}` and `{{ urlQuery ... }}` too
- links: the link scanner skips html blocks (a line starting with a block tag like `<div>` up to the next blank line) and the yaml front matter like the rendered page does, so a markdown link there is no used link and rename, move and media relocation don't rewrite it. an html block that should still carry links has to be separated by a blank line from the markdown around it. nothing to do
- links: renaming or moving a media file (or a doc with a relative media link) now writes a relative media link with its `media/` segment (`./media/x.png`, `../media/x.png`) instead of `./x.png`, so it no longer depends on a docs file of the same path being absent. nothing to do
- files: a path without `docs/` or `media/` prefix that starts with a folder called `files` (`files/notes.md`) is now that docs folder instead of being read as `notes.md`. the wikilink autocomplete of `[[docs/<path>#` now suggests the headings of the docs file `<path>`. nothing to do
